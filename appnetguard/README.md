# AppNetGuard — per-app internet kill switch for iOS (Flutter)

AppNetGuard lets you pick apps on an iPhone or iPad and cut their internet access with a
single toggle, while every other app keeps working. Flip the switch back and the app is
online again.

The UI is Flutter. The blocking itself is native: an Apple **Network Extension content
filter** (`NEFilterDataProvider`) that runs inside iOS, sees every new socket flow together
with the identifier of the app that opened it, and drops the flow when that app is on your
block list.

## ⚠️ Read this first: iOS only runs content filters on supervised devices

This is an Apple platform restriction, not something the app can work around:

* A content filter is the **only** iOS API that can tell which app a network connection
  belongs to and block it. A local VPN (`NEPacketTunnelProvider`) sees packets but not
  their source app; Screen Time "shields" hide the whole app instead of just its network.
* iOS allows content filters **only on supervised devices** — devices enrolled in MDM or
  supervised with Apple Configurator. On an unsupervised device the master toggle fails and
  the app shows a "supervised devices only" message.

To supervise your own test device with Apple Configurator (free, Mac App Store):

1. Back up the device — supervising erases it.
2. Connect it to the Mac, open Apple Configurator, select the device, choose
   **Actions ▸ Prepare…**, pick *Manual configuration*, tick **Supervise devices**, and
   follow the prompts (you can skip MDM enrollment).
3. Restore your backup after the device restarts; supervision survives the restore.

```
└── ios/

    │                              FilterExtension target and entitlements
    ├── Runner.xcworkspace         Open THIS in Xcode
    ├── Runner/
    │   ├── AppDelegate.swift      Registers the method channel
    │   ├── FilterChannel.swift    NEFilterManager + rule store, exposed to Dart
    │   └── Runner.entitlements    content-filter-provider + App Group
    ├── FilterExtension/
    │   ├── FilterDataProvider.swift   Drops flows from blocked apps
    │   ├── Info.plist, FilterExtension.entitlements
    └── Shared/                    Compiled into both native targets
        ├── AppRule.swift          Codable rule + bundle-identifier validation
        ├── RuleStore.swift        App Group UserDefaults persistence
        └── RuleMatcher.swift      Matches flow identifiers against blocked bundle IDs
```

How the pieces talk to each other:

1. Flutter calls the `com.skystarsweet.appnetguard/filter` method channel
   (`getState`, `setFilterEnabled`, `addRule`, `setBlocked`, `removeRule`, `setAllBlocked`,
   `clearSeen`). Every call answers with the full state.
2. `FilterChannel.swift` writes rules to the shared **App Group**
   (`group.com.skystarsweet.appnetguard`) and bumps a revision counter; it also enables or
   disables the system filter through `NEFilterManager`.
3. The extension checks the counter on every new flow and re-reads the rule list only when
   it changed, so the per-flow cost is one integer read and a set lookup.
4. The extension records every app identifier it sees, so the **Add app** sheet can offer
   a "Recently seen" list — you do not need to know bundle identifiers up front.
5. When the filter configuration changes outside the app, iOS posts a notification and the
   native side pushes `stateChanged` to Dart.

## Building and running

Requirements: macOS with Xcode 15+, Flutter 3.47+ (stable), an Apple Developer account, a
physical iPhone/iPad on iOS 15+. Network Extensions do **not** run in the Simulator.

```sh
cd appnetguard
flutter pub get
open ios/Runner.xcworkspace
```

1. In Xcode select the **Runner** target ▸ *Signing & Capabilities* and choose your Team.
   Do the same for the **FilterExtension** target. Xcode registers the App IDs for you.
2. If Xcode complains about capabilities, make sure both App IDs have **Network Extensions**
   and **App Groups** enabled in the
   [developer portal](https://developer.apple.com/account/resources/identifiers/list), and
   that the App Group `group.com.skystarsweet.appnetguard` exists. If you change the bundle
   identifiers or the App Group name, update them in:
   * both targets' build settings (`PRODUCT_BUNDLE_IDENTIFIER`),
   * `ios/Runner/Runner.entitlements` and `ios/FilterExtension/FilterExtension.entitlements`,
   * `ios/Shared/RuleStore.swift` (`AppGroup.identifier`).
3. Pick your device and press **Run** in Xcode, or from the terminal:

   ```sh
   flutter run -d <device-id>
   ```

4. In the app, turn on **Network filter**. iOS asks you to allow the content filter.
5. Tap **Add app**, choose an app (preset, recently seen, or type its bundle identifier),
   and it is blocked immediately. Toggle any row to allow or block that app again. Swipe a
   row left to delete it.

### Checking it works

Add YouTube (`com.google.ios.youtube`) and block it. Open YouTube: feeds fail to load and
videos will not play. Toggle it back on; new connections succeed right away (an app may keep
a stale error screen until you pull to refresh).

Extension logs are visible in Console.app under the subsystem `com.skystarsweet.appnetguard`.

### Tests

```sh
flutter analyze

```

The widget tests fake the native channel, so they run on any platform.

## Behaviour details

* Blocking is by the app's **code-signing identifier**. The matcher accepts both the bare
  bundle ID (`com.example.app`) and the team-prefixed form (`ABCDE12345.com.example.app`).
* Only flows with an attributable source app are examined; system daemons without an app
  identifier are always allowed.
* Rules persist across launches and reboots. The filter stays active in the background
  until you turn it off or delete the app.
* Extension and app share `FLUTTER_BUILD_NAME` / `FLUTTER_BUILD_NUMBER`, so their versions
  always match (App Store validation requires this).

## Known limitations

* **Supervised devices only** on iOS (see above). This also means the app cannot ship on
  the App Store as a general-purpose consumer firewall.
* Blocking is all-or-nothing per app; there is no Wi-Fi vs. cellular split and no per-domain
  allow list (both are straightforward extensions of `RuleMatcher` / `FilterDataProvider`).
* Apps that share a network process (for example some browsers' helper processes) are
  identified by whichever bundle actually opened the socket.
* Only iOS is wired up. `flutter create --platforms ios` was used, so there is no Android
  project; the Dart code degrades to an "unavailable" state anywhere without the native side.
